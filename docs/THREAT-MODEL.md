# What each party can do (1.4)

Who can do what to a VoIPC user, as of 1.4, and what in the code holds each
"cannot". Tests are named so they can be found with a search; `test-ui` checks
run in the browser lanes of `test-web.sh`.

| Who | Can | Cannot | Held by |
|---|---|---|---|
| **The relay, honest or only curious** | See metadata: who is connected and from which address, which channel, when, and how big each packet is. With accounts, also what [ACCOUNTS.md](ACCOUNTS.md) lists for kept messages: who wrote where, when, how long, and each copy's timer. For files posted in chat: each blob's size, when it is uploaded and fetched and by which connection, and which conversations it was posted or forwarded in (which links them); a re-upload shows which members still hold it. | Read messages, voice, video, screen audio, positions, kept copies or vault items. Read a file, or learn its name or type: each is sealed under its own key, which only the end-to-end message carries. | libsignal sessions; `media_keys` (AES-256-GCM); `log::seal_entry`; the vault (`account::Vault`); `voipc_crypto::file` (`known_answers`). |
| **The relay, actively hostile, for desktop users** | Meet guests in the middle: a guest's identity is per connection and not verified, by design. Seat a listener in a channel (the member list shows it). With accounts: meet you before the person you meant to meet; hide, drop or roll back vault items, the pins included; withhold kept copies or hand them out again; guess a password offline, at 600,000 PBKDF2-SHA256 rounds a guess; keep a writer on an old key of their own, which helps it only together with a member who left. | Read kept copies or vault items without the password. Forge or alter a member's kept entry (each is signed). Add a reader without the writer's device naming them. Replace a pinned key unnoticed, unless it removes the pins first, and then a device that saw them warns. Hand out a name no account could have (a letter from another script that looks like a Latin one, an invisible character) without a warning: it is treated as a name taken over. Make one member's voice play as another's. Bring back entries already read, or a cleared conversation. Claim another relay's id to get a password stretched for that one. Hand over another file under a file's id, or one that opens differently for two members (the key is committed). It can withhold a file, or say nobody has it. | `a_rewritten_sender_fails`; `a_replayed_session_start_on_the_last_resort_key_is_refused`; `vault_pins_it_cannot_trust_are_reported_and_never_saved_over`; `a_merged_pin_that_disagrees_is_reported`; `a_look_alike_name_from_the_relay_is_a_warning`; `a_server_claiming_another_servers_relay_id_gets_nothing_of_the_password`; `AccountSync::drain` drops entries at or below the read cursor; `the_recovery_key_sets_a_new_password_and_signs_every_device_out` (the relay checks the identity's signature); `another_blob_is_not_this_file`; `another_key_is_refused_by_the_commitment`. |
| **The relay, actively hostile, for browser users** | Everything above, and serve a page that reads what you type (your password included) and takes the remembered device keys and vault keys this page keeps, for every server opened in it. | Nothing the page itself cannot do. | Only the desktop app; the connect dialog warns when an account is on another server than the page's own. test-ui: "a server claiming another's relay id is refused". |
| **A member of a channel** | Read what is said there while a member, and keep copies. Hand over history, which is shown as second-hand. Prove that you wrote a kept message (they are signed). Keep a message you deleted: every VoIPC app removes it, but a modified one need not, and anyone may have copied it first. Put any name and time on a forward: *Forwarded from* is the forwarder's word. In a direct conversation, with a modified app, notice when you open a file they sent you after the relay's copy has gone: the relay asks their app for it again. Only the conversation it is opened in is asked, so where else it was forwarded learns nothing. With a modified app, also ask whether your device still holds a file whose id they know from any conversation they are or were in, and make it upload the file again: they post a message naming the file in a conversation with you and fetch it there, and your app, which holds the file and now has a message about it, uploads it with nothing on screen. In a direct conversation the answer is about you; in a channel, about someone there. Each time the relay has let the file go, it costs your upload budget again. | Forge another member's message or kept entry. Fetch a file posted in a conversation they are not in, unless they hold its id, which only its messages carry (then they can file it under a conversation of their own; without the key the blob says nothing). Read what is written after they left a text channel (the relay takes them out of its log, and the next message is under a new key) or after the next media key once they left a voice channel. Offer a media key for a room they are not in. Speak as another member. Edit or delete your messages: each app checks the writer, and takes a guest's change only for what it received on that guest's connection. Pin a message where the member list does not show them as a manager of the channel. | `leaving_a_text_channel_ends_its_readership`; the media-key rules in `channel_state` and `media_keys`; `a_rewritten_sender_fails`; `only_its_conversations_may_fetch_and_an_unknown_hash_looks_the_same`; `a_blob_that_has_gone_is_asked_for_and_the_waiter_is_served`; `chat-rules.test.ts`: "an edit applies only from the message's writer, and marks it edited", "a guest changes only what this connection received from them (R3-11)", "a pin counts only from a manager, and the latest pin event wins". |
| **A member with privileges** (a group's, 1.7) | What their privileges say and no more: kick, ban, the ban list, channels, emotes, the account list and history (no addresses), giving groups, editing groups. A ban covers an address, and ends every session there that holds no privilege, so whoever bans learns which other people were connected from the banned person's address: they leave at the same moment. That is by design: a ban is meant to cover the household or office. With `voipc:modlog`, read who acted on whom, when and why (why someone was restricted, only with `voipc:restrict` too), for `modlog_days`, by the names they had, also of accounts since deleted. With a modified app, leave out or make up their own note of a hidden message, which the log marks as their app's word. | Change or delete a row of the moderation log, or write one in another's name: the actor is the session, and a note names its sender. Act unwritten: no row, no step. Read from the log who stands behind a pseudonym (the database holds no account for that row), a channel their gate hides, or who was in a channel hiding its members. Flood the log to push out a ban: only time takes a row, and notes stop at 120 an hour. Kick or ban an admin or anyone else with a privilege that acts on others (calling on everybody, taking reports and reading the moderation log act on nobody, and spare nobody). Hand out a privilege they lack, or act on an account holding one they lack. Give or take a group with privileges, or edit a group, without a fresh two-factor code. See behind an anonymous channel, or the roster of a channel that hides its members (admins only). See, join or change a gated channel they are not let into, or shut themselves out of one. See an address. | `each_privilege_grants_its_own_step_only`; `a_moderator_cannot_touch_admins_or_see_addresses`; `a_reports_only_holder_can_be_kicked_by_a_moderator_and_a_restrict_holder_cannot`; `the_modlog_is_read_by_its_privilege_only`; `a_log_reader_who_cannot_restrict_does_not_read_why_someone_was`; `no_row_no_step`; `a_masked_person_stays_masked_in_the_log`; `a_gated_channel_stays_hidden_in_the_log`; `a_note_is_marked_advisory_names_its_sender_and_is_capped`; `admin_steps_that_hand_out_power_ask_for_a_fresh_code`; `a_channel_editor_reaches_only_channels_it_may_see`; `a_channel_editor_cannot_switch_anonymity_off`; `account_bans_follow_the_account_and_roles_pass_address_bans`; l4f `roles_change_only_on_accounts_the_actor_covers`. |
| **Someone holding your Discord, Google or Facebook account** (1.8) | Sign in as far as the relay's question of what opens the account. Ask your other device for its vault key, three times and then once per ten minutes: you see the ask, and it needs you to compare a code and say yes. Claim an account linked to that provider that nobody has opened yet, which is then theirs. Where the move from Discord made that account (1.11): hold its badges, gates and name, skip the wait for new members if that member was long-standing, and hide or delete that member's imported posts. | Hold any power it had on Discord until the owner says OK, which the owner should check outside Discord first; after `admin reclaim` it waits for that OK again. Join a channel, read anything, or take your connection over without the vault: `AuthStep::ProviderSigned` never carries `slot.pass`, and only an identity signature gets past it. Replace an identity, even with your code. Unlink the last way in. | `a_hijacked_provider_account_gets_no_admission_and_takes_nothing_over`; `the_password_slot_never_goes_out_to_a_provider_sign_in`; `a_provider_and_a_code_cannot_replace_an_identity`; `asking_the_other_device_is_rate_limited`; `a_reclaimed_placeholder_holds_no_power_until_a_new_ok`. |
| **The provider itself** (1.8) | Everything above, for anyone using it, and see when they sign in here. | Read or open anything of VoIPC's: it gets no token or key from it, and is never told your account name. | The relay is the OAuth client; `voipc_crypto::account` derives nothing from a provider. |
| **A relay, about provider sign-in** (1.8) | Say an account was never opened, to hide its vault and the pins in it, then seat substituted keys as new: a device that remembers the account refuses, a new device only warns. Use the provider's id for you, which it stores. Swap the key in a pairing: it has one guess at a six-digit code for each time you compare. | Send your app to a copy of the provider's page: only the providers' own addresses are opened (`provider_page_ok`). Learn the vault key from a pairing: it is wrapped to a key committed to before the other device's nonce. | `a_remembered_account_is_not_believed_unopened`; `only_a_providers_own_page_is_opened`; `a_swapped_key_is_caught`; `the_vault_key_goes_only_to_the_committed_key_and_only_on_a_yes`. |
| **A member, about names and pictures** (1.9) | Choose a display name and a picture, seen by anyone on the server. Be cleared by `voipc:profiles`. | Pass for another account: the name cannot be theirs or look like it, and the app always shows the `@name` beside it (`a_name_cannot_pass_for_someone_elses`, `profile-names.test.ts`). Have a picture reach a WebView's decoder: every client sanitizes it first (`image-sinks.test.ts`). Learn who is in a channel hiding its people from a pushed change (`a_change_goes_to_the_people_who_see_the_row_and_to_nobody_else`). | The relay sees and keeps display names and pictures, and whose picture each person fetches. |
| **Anyone connected, about badges** (1.9) | Read every group's badge, a guest too, whoever holds it. A badge is a public label: a group that should stay secret should not have one. | Read what the group behind it is called, or who holds it where rows hide that. | `GroupStyles`, badges only. |
| **A relay, about names and pictures** (1.9) | Lie about a display name, a picture, a server's name, or who holds `voipc:mention_all`, so an app rings for a real member's message. | Hide the `@name` or the address: both are always shown. Have a server's name pass for an address or for another server here (`cleanServerName`). Write the message itself, or have it ring for a stored or handed-over copy (`mention-rules.ts`). | Text is end-to-end; names were always the relay's word (safety numbers are the check). |
| **Someone holding an invite link** (1.9) | Make accounts until its limit, expiry or revocation, each with the proof of work and the sign-up limits. Join its starting group. | Gain a privilege: the group must hold none when made and at each use (`a_starting_group_holds_nothing_when_made_and_when_used`). Skip the work (`a_link_does_not_stand_in_for_the_proof_of_work`). | |
| **Someone you blocked** (1.10) | See you, and write to you, as before: their messages are delivered and kept. Get around it, as a guest, with another name. Be heard for a moment as they join your call, and light up as speaking. | Learn from anything the app does that you blocked them: an invite is left unanswered, never declined, and nothing is refused. Reach you through a poke, an invite, a notification or a count. | `block-rules.ts`: a view only, on your device. Never a declined invite, a refused message or `SetAudioFilter`. |
| **A relay, about who you blocked** (1.10) | See that the vault item `item.blocks` exists, when it changed and its size to the nearest kilobyte. Hold back or roll back a copy, which a device that saw a newer one reports. A guest's list it never sees. | Read who is on it, or how many, within a kilobyte. Learn it from anything else: the mixer, the unread counts and the lists stay on the device, and a block sends nothing but that one sealed write. | The vault (`account::Vault`), padded to 1 KiB (`sync::Blocks`); `a_block_sends_one_sealed_write_and_names_nobody`. |
| **A moderator, about speech** (1.10) | Stop a member's voice and screen share, and with a timeout their posts, pokes, invites, new channels, and setting a name or picture, for as long as they choose. A guest's goes by address, for a day at most, and holds every guest behind it; one off posts who connects again goes by `guest` and their tag. It also marks each of those guests for everyone connected, so everyone can see that they share an address, though not which, also when one of them goes by a pseudonym. That is by design, as with a ban: it is meant to cover the household or office. A moderator can use it to find out who shares one, at the cost of a row in the log each time and with nobody disconnected. | Read anything by it: a restriction reads nothing. Reach direct messages, so a person cut off in every channel can still appeal or report. Take keys, which they would need after the lift. Act on anyone holding more than they do, or on an admin, also through a guest at a token admin's address. Lift their own. Act unseen: everyone is told who is held, by whom and until when, and the log keeps the row. Waive the wait for new members, except by giving a group. | `only_someone_holding_at_least_as_much_acts_on_a_holder`; `a_held_moderator_cannot_lift_their_own_restriction`; `a_token_admin_is_spared_from_a_moderator`; `a_token_admin_is_not_held_by_a_row_on_their_address`; `a_guest_off_posts_does_not_choose_a_new_name`; `a_moderators_restriction_leaves_direct_messages_and_kept_direct_copies_open`; `key_relays_still_pass_while_restricted`; `set_and_lift_write_rows_and_expiry_the_wait_and_a_refusal_do_not`; `what_cannot_be_kept_does_not_happen`; `lifting_what_no_moderator_set_is_refused_and_the_wait_stays`. |
| **A relay, about restrictions** (1.10) | Drop anyone's voice or posts without a word, as it always could. Say whatever it likes about who is held, by whom, until when and why: marks, names and times are its word, and no app can check them. See the reason a moderator gives, and hand it to whoever it wants. | Read a post it drops. Put words in anyone's mouth by it. | The relay's end-to-end rules, as the rows above. |
| **A moderator, about what people read** (1.10) | Collapse a message in a channel, with their name on it, for everyone whose app obeys. See it counted while they are away and after, until the privilege goes, except by someone who joined after the hide: it sits under the moderator's own key, so they read the message unhidden until that moderator's app is back, and for good if that moderator shares no history with newcomers. Be left out of the log by a changed app: the row is their own app's word. | Destroy or change a word of it: every copy keeps it, and *Show anyway* opens it. Reach a direct conversation, an anonymous channel, or the words of anyone holding a privilege, unless they are an admin. | `hideRight`, `applyEvent` in `chat-rules.ts`: `a_note_is_marked_advisory_names_its_sender_and_is_capped`. |
| **A moderator, about what the server keeps** (1.10) | With a fresh code, and with `voipc:ban` or `voipc:bans`, delete for good what someone banned now wrote to channels' stored logs in the last seven days, an admin all of it, and collapse their copies on everyone's devices with their own name on the line. That also takes their imported posts in the span (1.11), by when they were written, also if they have since taken Discord off the account. Lifting the ban restores nothing. A limited window can bring back an older message the writer deleted or edited, for devices reading the log anew: their delete or edit is a row of theirs and goes, and the older row stays. An admin's removal of someone banned behind a pseudonym deletes by the account and tells that admin the real name. | Remove anything of someone who is not banned now, or of someone holding a privilege, unless an admin. Delete direct messages, or anything from a device, or the keys a writer goes on using. Act unwritten: the delete and its row are one transaction, and the row says how many went. Go further than seven days without `*`. Unmask a pseudonym: a moderator has only that name, which deletes nothing; a real name asked against that ban answers as for someone not banned, also for a ban an admin made; and the row and what every app is told, online or connecting later, hold only the pseudonym. | `remove_posts_needs_a_ban`; `a_ban_privilege_is_what_lets_someone_remove`; `remove_posts_takes_only_channel_rows_in_the_window`; `a_removal_that_cannot_be_kept_deletes_nothing`; `a_moderator_cannot_remove_the_posts_of_a_privilege_holder`; `only_an_admin_removes_more_than_seven_days`; `remove_posts_asks_for_a_fresh_code`; `a_removal_behind_a_pseudonym_stays_masked`; `a_real_name_cannot_be_tried_against_a_pseudonyms_ban`; `a_pseudonym_is_not_the_account_of_that_name`; `readers_open_what_is_left_after_a_removal`; `a_writer_back_from_a_temporary_ban_can_post_again`. |
| **A relay, about removed posts** (1.10) | Say anyone's posts were removed, with anyone's name as who did it: the line is its word, signed by nobody, and it says so. That collapses copies behind one extra click. It could always drop stored messages silently, and a gap is no attack here: nothing chains an entry to the one before. | Erase a copy on a device with this: it is the field a hide uses, never the deletion marks, and Show anyway stays. Touch a direct conversation on a device. Learn anything new: it already knows who wrote what and who is banned. | `a mark hides and never deletes`, `a direct conversation is the other party's too`; `a_guests_ban_hides_by_name_and_deletes_nothing`; `everyone_hears_posts_hidden_and_a_newcomer_hears_it_at_connect`. |

| **A relay, about hiding** (1.10) | Name any account as a holder, or none: the list is its word, which no app can check. | **Anyone connected, about who holds privileges** (1.10) | Learn every account holding a privilege other than taking reports, reading the log or calling on everybody, and which of them hold `voipc:hide` or everything, a guest too. | **Anyone connected, about who is held** (1.10) | See that someone is held, by whom and until when, under the user id any roster already shows, a guest too. | **A moderator, about who comes in** (1.10) | With `voipc:channels`, ask anyone online into a room they stand in, past its password, which they could change anyway. | **A member outside a gate, about reports** (1.10) | Write to a moderator standing in a hidden channel, as to anyone: that is how a report reaches them, and it is all it takes. | Post in that channel, hand it a sender key or read its log: a report opens no door. What changed for 1.0: post-quantum sessions, the sender in the media AAD, pre-key
refill, rolled-back or missing vault items reported instead of reset, a known
account shown as a guest reported, cleared direct conversations kept cleared,
the relay-id check in the browser, and readership ending when you leave a text
channel.

What changed for 1.3: files. A message's destruction timer, or a cleared
conversation, does not reach the relay's copy of a file it carried. That copy
is ciphertext, and goes within `max_age_hours` (24 h by default) of its latest
upload (a member's app uploads it again when someone asks after it has gone),
or with the next restart. The blob's exact size shows; it is not padded (readers
accept padding inside the sealed body, so a later version can add it). A guest's
side of a direct conversation is that guest's connection: another guest who takes
the same name later is not in it, and is not asked for its files.

What changed for 1.4: pictures, and emotes. **No picture somebody else made reaches
the app's or the browser's own image decoder** (a crafted one there, as libwebp's
CVE-2023-4863 was, would run code in the app). Every chat picture, emote and sticker
is decoded by memory-safe Rust (`crates/voipc-media`: pure-Rust decoders that forbid
`unsafe`, under fixed budgets), and only a PNG it wrote is shown; a picture it will not
read is offered to save, never shown (`what_is_too_big_is_refused_before_anything_is_allocated_for_it`,
`a_damaged_picture_is_refused_at_every_length_and_never_panics`, the `media` fuzz target,
`image-sinks.test.ts`); an animation that runs past a budget after its first frame is read no
further and shown as that frame, with a note saying why
(`an_animation_over_a_budget_stands_as_its_first_frame_and_says_why`). A relay sets how much
of a moving picture its members' apps keep
(`[files] animation_side`, `animation_mb`), within bounds each app holds it to
(`FileLimits::animation`), so a relay cannot make one picture take more than 512 MiB. Video
and sound still play through the system's decoders, after
a click, where the person allows it: on by default except in the Linux desktop app, whose
web view runs outside any sandbox. Emotes are the server's own, kept readable on the
relay like its channel names; the relay never decodes them, and an admin or a hostile
relay can show members a picture, never make one run. A message binds the hash of the
emote its sender saw (128 bits of it since 1.5; 1.4's 80 left room for a planned
collision), so an emote changed later shows as its name, not as another picture
(`emote-rules.test.ts`). Every member's app fetches every emote, so fetches say
nothing about who used which.

The desktop keeps a one-time copy of a 1.0 history beside the new one
(`chat_history.bin.v5`, under the same password), so that 1.0 can be gone back to.
Destruction timers and a purge do not reach that copy; clearing or deleting the history
removes it (`the_copies_kept_for_an_older_voipc_go_with_the_history`).

Edits, deletes, reactions and pins (1.3) are end-to-end encrypted messages like any
other: the relay sees one more message in that conversation, and counts it as a post in
an announcement channel or under slow mode. Someone who joins a channel later and is
handed its history gets edits applied and deleted messages left out, but no reactions
and no pins.

Also in 1.3: a password reset proves the recovery key itself, through a reset key it
derives (`slot.reset`, kept by the relay). Before, the vault key that every remembered
device keeps was enough, so a remembered device, or one forgotten at a password change,
could set a new password on an account without two-factor codes and sign everyone else
out. An account made before 1.3 keeps that gap until its owner makes a new recovery key
([ACCOUNTS.md](ACCOUNTS.md)).
